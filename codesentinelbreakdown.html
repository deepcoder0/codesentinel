06 — Prompt Engineering
The Prompts ARE the Product

In an LLM system, the prompt is 80% of the quality. Here's the actual prompt architecture — system prompt skeleton, structured output format, few-shot examples, and RAG context injection. Every agent follows this template.

Quality Agent — System Prompt (v1)

## ROLE
You are a senior code reviewer specializing in code quality and maintainability.
You review ONLY the changed lines in a pull request diff. You do NOT review
unchanged code or make assumptions about code outside the diff.

## KNOWLEDGE CONTEXT
The following coding standards and team conventions apply to this review:
---
{rag_context}
---
Use these standards as authoritative reference. Cite specific rules when flagging issues.

## REVIEW CHECKLIST
Evaluate the diff against these criteria (in priority order):
1. Naming clarity — variables, functions, classes should reveal intent
2. DRY violations — repeated logic across changed files
3. Cyclomatic complexity — deeply nested conditionals (>3 levels)
4. Dead code — unused imports, unreachable branches
5. Type hints — missing annotations on public function signatures
6. Docstrings — missing on public classes and functions

## A2A QUERIES
If you encounter a finding that would benefit from another agent's expertise,
emit an A2A query. Examples:
- You're unsure if a pattern matches team conventions → ask architecture_agent
- You spot a code pattern that might have performance implications → ask performance_agent
Maximum 3 queries per review. Use the structured format below.

## OUTPUT FORMAT
Respond with ONLY valid JSON. No markdown, no explanation outside the JSON.

{
  "findings": [
    {
      "file": "src/api/routes.py",
      "line_start": 42,
      "line_end": 42,
      "severity": "warning",          // "critical" | "warning" | "info"
      "category": "naming",           // from checklist above
      "message": "Variable 'x' is unclear — suggest 'user_count'",
      "suggestion": "user_count = get_active_users()",
      "confidence": 0.85              // 0.0 - 1.0, how sure you are
    }
  ],
  "a2a_queries": [
    {
      "to_agent": "architecture_agent",
      "query_type": "convention_check",
      "query": "Is there a naming convention for service layer variables?",
      "context": {"file": "src/api/routes.py", "line": 42}
    }
  ],
  "summary": "Found 3 issues: 1 warning (naming), 2 info (type hints)."
}

## FEW-SHOT EXAMPLE
Given this diff:
  + def calc(a, b):
  +     return a * b + a / b

Your response:
{
  "findings": [
    {
      "file": "utils.py", "line_start": 1, "line_end": 2,
      "severity": "warning", "category": "naming",
      "message": "Function 'calc' and params 'a', 'b' don't reveal intent",
      "suggestion": "def calculate_rate(principal, rate): ...",
      "confidence": 0.9
    },
    {
      "file": "utils.py", "line_start": 1, "line_end": 1,
      "severity": "info", "category": "type_hints",
      "message": "Missing type hints on public function",
      "suggestion": "def calc(a: float, b: float) -> float:",
      "confidence": 0.95
    }
  ],
  "a2a_queries": [],
  "summary": "Found 2 issues: 1 warning (naming), 1 info (type hints)."
}

Why This Structure Works

Role anchoring — tells the model WHO it is, scopes behavior. RAG injection point — retrieved knowledge placed BEFORE the task, not after, so it's in working memory. Structured output — JSON schema prevents freeform prose, makes parsing reliable. Few-shot example — one concrete input→output pair calibrates format better than 100 words of instruction. Confidence score — forces the model to self-evaluate, reduces false positives.

Prompt Versioning Strategy

Every prompt lives in /prompts/ as versioned markdown files. PROMPTS.md logs every change with rationale: "v1→v2: added confidence field, reduced false positives by 15%." This is how you prove prompt engineering isn't just vibes — it's measurable iteration. In an interview, you can walk through your v1→v2→v3 evolution and explain why each change improved quality.

Agent Prompt Differences

All 4 agents share the same template structure (role → knowledge → checklist → output format) but differ in: the ROLE definition, the CHECKLIST items, the RAG collection queried, the severity calibration (security defaults higher than quality), and the A2A query examples. The Security Agent's prompt includes OWASP references in its few-shot. The Architecture Agent's prompt is the most RAG-dependent — its checklist comes almost entirely from retrieved team conventions.
07 — Agent-to-Agent Communication
Agents That Actually Talk to Each Other

Most "multi-agent" projects on GitHub are just parallel execution — agents work in isolation and a merger combines outputs. CodeSentinel goes further: agents can query each other mid-review for cross-domain context, producing richer findings than any single agent could alone.

Why This Changes Everything

Without A2A, each agent reviews code in its own silo. The Security Agent sees a hardcoded DB URL and says "move to env variable." That's correct but shallow. With A2A, the Security Agent asks the Architecture Agent: "What's this team's config management pattern?" Architecture checks its RAG collection and responds: "Team uses pydantic-settings BaseSettings, see ADR-007." Now the Security Agent's finding says: "Hardcoded DB URL violates your team's config standard (ADR-007). Migrate to BaseSettings pattern in settings.py." That's a 10x better review.

This is the difference between "we ran 4 LLMs in parallel" and "we built a collaborative intelligence system." In an interview, this is where you explain why multi-agent is better than single-agent — not just because agents specialize, but because they cross-pollinate knowledge through structured communication.

The A2A Message Protocol

Agent-to-agent communication in CodeSentinel uses a structured message-passing protocol through the LangGraph shared state. It's not free-form chat — it's typed, bounded, and auditable.

class A2AMessage(BaseModel):
    """Structured inter-agent communication message."""
    id: str                          # unique message ID
    from_agent: AgentRole            # security | quality | performance | architecture
    to_agent: AgentRole              # which agent should respond
    query_type: QueryType            # CONVENTION_CHECK | PATTERN_VERIFY | CONTEXT_REQUEST | IMPACT_ASSESS
    query: str                       # natural language question
    context: Dict                    # file, line_range, finding that triggered this
    priority: int                    # 1-3, determines if query gets processed
    response: Optional[str] = None   # filled by responding agent
    responded: bool = False

class QueryType(str, Enum):
    CONVENTION_CHECK  = "convention_check"    # "What's the team's pattern for X?"
    PATTERN_VERIFY    = "pattern_verify"      # "Is this pattern used elsewhere in the codebase?"
    CONTEXT_REQUEST   = "context_request"     # "What's the intent behind this function?"
    IMPACT_ASSESS     = "impact_assess"       # "Would fixing X break Y?"
Phase 1 — Review + Emit Queries

Agents Review & Ask

All 4 agents review the PR diff in parallel (fan-out). While reviewing, each agent can emit A2AMessage queries into the shared state when it encounters a finding that would benefit from cross-domain context. These queries are appended to state["a2a_messages"]. Max 3 queries per agent per review to keep costs bounded.

Phase 2 — Route & Respond

Targeted Agents Answer

A process_a2a_queries node groups pending messages by to_agent. Each targeted agent gets a second LLM call with its RAG context + the questions addressed to it. It fills in the response field. This is a single extra LLM round — not an unbounded conversation.

Phase 3 — Enrich & Merge

Findings Get Enriched

Responses flow back to the originating agent. An enrich_reviews node updates the original findings with A2A context — the security finding now includes the architecture team's convention, the performance finding now cites the quality agent's pattern analysis. Enriched reviews go to the conflict resolver.

Design Decisions — Interview Ammo 🎯

Q: "Why not let agents chat freely in a loop?"
Unbounded multi-turn conversation between agents creates cost explosion, latency issues, and potential infinite loops. CodeSentinel uses exactly one query-response round — agents ask during Phase 1, respond during Phase 2, enrich during Phase 3. Bounded, predictable, auditable. This mirrors how real teams work: you ask a focused question, you get an answer, you move on.
Q: "Why message passing through state vs direct function calls?"
State-based messaging gives you full observability — every A2A query is logged in the state, visible in LangGraph Studio, and auditable after the fact. Direct function calls couple agents tightly and make the communication invisible. With state, you can answer "why did the Security Agent suggest pydantic-settings?" → because Architecture Agent told it to, and here's the exact exchange.
Q: "How do you prevent query storms?"
Three guardrails: (1) Max 3 queries per agent per review — enforced in the agent prompt and validated in code. (2) Priority field — only priority 1-2 queries get processed under time pressure. (3) Query type enum constrains what agents can ask — no open-ended "what do you think?" messages, only structured CONVENTION_CHECK, PATTERN_VERIFY, CONTEXT_REQUEST, or IMPACT_ASSESS.
Q: "How is this different from just making one big prompt?"
A single prompt with "check quality, security, performance, and architecture" gives you a mediocre generalist. Specialized agents with their own RAG collections produce deeper, domain-specific findings. A2A adds cross-domain insights that even the specialized agents can't achieve alone — the security agent doesn't know your team's config pattern, but it knows to ask the architecture agent. Decomposition + collaboration > monolith.
Q: "What's the latency impact of adding A2A?"
One extra LLM round. The response phase batches all queries per agent into a single call — so if Architecture Agent receives 3 queries from different agents, it answers all 3 in one LLM invocation. On Ollama (local), this adds ~10-15 seconds. On Claude API, ~3-5 seconds. Worth it for the quality uplift. The enrichment phase is pure code (no LLM), sub-100ms.

Updated LangGraph Node Sequence

Node 1: parse_pr           → Extract diff, build FileDiff objects
Node 2: fan_out_agents     → Send() to 4 agents in parallel
Node 3: quality_agent      ┐
Node 4: security_agent     │ Each agent: review diff + emit A2A queries into state
Node 5: performance_agent  │ Max 3 queries per agent, typed as A2AMessage
Node 6: architecture_agent ┘

Node 10: enrich_reviews    → Merge A2A responses back into original findings

Node 13: post_comment      → Push to GitHub API

  IF len(a2a_messages) == 0 → skip to Node 11 (no A2A needed, save latency)
  ELSE → proceed to Node 8 (run A2A round)
08 — Extensibility
Add Your Own Agent in 3 Steps

The system is designed to be pluggable. Adding a 5th agent (Testing Agent, Accessibility Agent, Documentation Agent) should take under an hour. Here's how.

BaseAgent Interface

from abc import ABC, abstractmethod
from codesentinel.models.review import ReviewItem
from codesentinel.models.diff import FileDiff
from codesentinel.models.a2a import A2AMessage

class BaseAgent(ABC):
    """All agents inherit from this. Implement review() and respond_a2a()."""

    name: str                          # e.g., "testing_agent"
    description: str                   # shown in MCP tool schema
    rag_collections: list[str]         # which ChromaDB collections to query
    prompt_template: str               # path to /prompts/testing_v1.md

    @abstractmethod
    async def review(self, diffs: list[FileDiff], rag_context: str) -> tuple[list[ReviewItem], list[A2AMessage]]:
        """Review the diff. Return findings + optional A2A queries."""
        ...

    @abstractmethod
    async def respond_a2a(self, queries: list[A2AMessage], rag_context: str) -> list[A2AMessage]:
        """Answer A2A queries from other agents using your domain expertise."""
        ...

    def get_mcp_schema(self) -> dict:
        """Auto-generate MCP tool schema from this agent's interface."""
        return {
            "name": f"check_{self.name.replace('_agent', '')}",
            "description": self.description,
            "input_schema": {"type": "object", "properties": {"code_snippet": {"type": "string"}}}
        }
01

Create the Agent Class

Create src/codesentinel/agents/testing.py. Extend BaseAgent, implement review() and respond_a2a(). Define your checklist and RAG collections. Write the prompt template in /prompts/testing_v1.md.

02

Register It

The agent registry auto-discovers any class that inherits BaseAgent in the agents/ directory. Just drop the file in. The LangGraph orchestrator's fan-out reads from the registry — your agent is automatically added to the parallel execution.

03

Add Knowledge (Optional)

Drop markdown files into /knowledge/testing/ and run make ingest. A new ChromaDB collection is created. Your agent's rag_collections field points to it. The MCP server auto-registers a new tool from get_mcp_schema().

The MCP layer is what makes this project future-proof. By exposing each agent as an MCP tool, anyone running Claude Desktop, Cursor, or any MCP client can invoke CodeSentinel's review agents natively — like a built-in extension.

What is MCP?

Model Context Protocol is an open standard (by Anthropic) that lets AI models call external tools and services. Think of it as "USB-C for AI" — a universal interface between LLMs and the tools they use. Exposing your agents as MCP tools means any MCP-compatible client can use them.

Why This Matters for Your Resume

MCP adoption is exploding. Claude Desktop, Cursor, Windsurf, Cline — all support MCP. But almost nobody is building MCP servers yet. Having a production MCP server on your GitHub separates you from 99% of candidates.

10 — RAG Pipeline
Knowledge-Grounded Reviews

Agents don't just rely on their training data. They query a curated knowledge base at runtime — coding standards, OWASP guidelines, team conventions — for context-aware, authoritative reviews.

01

Ingest

Load documents: OWASP Top 10, Python style guides, Clean Code principles, custom team ADRs. Support .md, .txt, .pdf sources.

02

Chunk

Split into semantic chunks using RecursiveCharacterTextSplitter with code-aware separators. ~500 tokens per chunk, 50 token overlap.

03

Embed

Generate embeddings locally using all-MiniLM-L6-v2 via Sentence Transformers. Zero API cost. 384-dim vectors.

04

Store

Index into ChromaDB collections — one per knowledge domain (security, quality, performance, architecture). Metadata tags for filtering.

05

Retrieve

At review time, each agent queries its relevant collection with the code context. Top-k=5 chunks returned, re-ranked by relevance.

06

Augment

Retrieved chunks injected into agent prompt as context. The agent now reviews code against authoritative standards, not just vibes.

11 — Error Handling & Resilience
What Happens When Things Break

Production systems aren't defined by the happy path — they're defined by how they handle failure. Every failure mode in CodeSentinel has a documented strategy.

LLM Returns Garbage JSON

The most common failure. Agent sends a prompt, Ollama returns malformed JSON or prose instead of the expected schema.

Strategy: Retry with repair prompt (max 2 retries) → if still fails, return empty findings with error metadata → pipeline continues with partial results → logged as "parse_failure" in observability

Ollama Timeout / OOM

Large diffs can exceed model context window or cause Ollama to hang on limited hardware.

Strategy: 60s timeout per agent call → on timeout, chunk the diff into smaller pieces and retry → if still fails, skip agent with "timeout" status → circuit breaker: if agent times out 3x consecutively, disable it for 10 minutes

GitHub API Rate Limit

GitHub's API has a 5,000 req/hour limit. Busy repos could exhaust this.

Strategy: Check X-RateLimit-Remaining header before each call → exponential backoff on 403 → cache PR diffs in SQLite for re-reviews → webhook deduplication (ignore duplicate PR events within 30s window)

One Agent Crashes Mid-Review

Security Agent throws an unhandled exception while the other 3 are running.

Strategy: Each agent runs in try/except wrapper → failed agent returns empty result with error status → other agents' results still collected and processed → final comment notes "Security review unavailable — agent error" → full traceback in observability logs

RAG Retrieval Returns Irrelevant Chunks

ChromaDB returns chunks that don't match the code context (low relevance scores).

Strategy: Minimum similarity threshold (0.7) → chunks below threshold discarded → agent prompt includes "If no relevant standards found, use your general knowledge" fallback → retrieval quality tracked in metrics

Massive PR (100+ files changed)

Some PRs are huge — refactors, dependency bumps, generated code.

Strategy: File limit cap (configurable, default 30) → prioritize by change type (modified > added > renamed) → skip generated files (detected by path patterns) → comment includes "Reviewed 30/127 files — prioritized by change significance"

Every LLM call logged with: agent name, prompt version, model used, input tokens, output tokens, latency (ms), success/failure, structured output parse success. Integrated with LangFuse (free tier) or LangSmith for visual trace exploration. Each review gets a trace_id that links all sub-calls.

13 — Human-in-the-Loop
When the Agent Isn't Sure, Ask the Developer

LangGraph's interrupt() feature lets you pause the pipeline, surface an uncertain finding to the developer, and resume with their input. This is the difference between an automated tool and a collaborative reviewer.

When It Triggers

Low Confidence Findings

When any agent produces a finding with confidence < 0.5, the pipeline pauses. The finding is surfaced as a pending question: "Security Agent found a potential SQL injection at line 42, but isn't sure (confidence: 0.35). Should this be flagged?" Developer responds via API or Slack integration.

How It Works

LangGraph interrupt()

The resolve_conflicts node checks for low-confidence findings. If found, it calls interrupt({"pending_findings": [...]}). The graph state is checkpointed. When the developer responds, the graph resumes from the checkpoint with their input merged into state.

Developer Response Options

Confirm, Reject, or Skip

Confirm → finding included in final review with "developer-verified" tag. Reject → finding dropped, logged as false positive for prompt tuning. Skip / timeout (5 min) → finding included with "unverified" label. All responses feed back into eval metrics.

Interview Angle

Human-in-the-loop is the feature that makes senior interviewers pay attention. It shows you understand that AI systems need guardrails, that confidence-aware outputs are better than binary yes/no, and that LangGraph's checkpointing + interrupt model is how production agentic systems handle uncertainty. Most multi-agent demos are fully autonomous — yours has a collaboration point where humans and agents work together.

The parser is the "eyes" of the entire system. If the diff extraction is wrong — missing context lines, garbled hunks, wrong line numbers — every agent downstream produces garbage. ?
Why This Is 2 SP

This is the backbone of the entire project. The LangGraph state machine defines how data flows through the system — what gets computed, in what order, and how state is passed between nodes. Getting this right early means every future feature (agents, A2A, HITL) slots in cleanly. Getting it wrong means rewriting everything in Sprint 3. →
How — Step by Step
  • Define ReviewState — A TypedDict: { pr_url: str, diff_files: List[FileDiff], agent_reviews: Dict[str, List[ReviewItem]], final_output: str, metadata: Dict }. This is the single object passed through every node
  • Create parse_pr node — Takes state, calls the parser from CS-002, writes diff_files into state
  • Create quality_review node — Takes state, reads diff_files, formats them into a prompt, sends to Ollama via ChatOllama, parses JSON response into List[ReviewItem], writes to agent_reviews["quality"]
  • Create format_output node — Reads agent_reviews, generates markdown summary
  • Wire the graph — graph.add_node("parse", parse_pr) → graph.add_node("review", quality_review) → graph.add_node("format", format_output) → graph.add_edge("parse", "review") etc.
  • Test end-to-end — graph.invoke({"pr_url": "..."}) → check that final_output has markdown content
◆
Concepts You'll Learn
  • StateGraph — LangGraph's core class. You define a state schema (TypedDict), add nodes (functions that read/write state), and add edges (transitions). It compiles into a runnable graph
  • Nodes are just functions — Every node is def node(state: ReviewState) -> dict. It reads what it needs from state, does work, returns a partial dict to merge back. Like Lambda functions in Step Functions
  • ChatOllama — LangChain's wrapper around Ollama's API. ChatOllama(model="qwen2.5-coder:7b") gives you a chat interface. .invoke([SystemMessage(...), HumanMessage(...)])
  • Structured output parsing — Tell the LLM to return JSON matching your Pydantic model. Parse with json.loads() and validate with ReviewItem(**data). Handle parse failures with a repair prompt
  • TypedDict vs Pydantic — TypedDict for state (lightweight, dict-like). Pydantic for data models (validated, serializable). LangGraph requires TypedDict for state
!
Gotchas & Tips
  • State merging — When a node returns {"agent_reviews": {...}}, LangGraph shallow-merges it into state. For nested dicts, this can overwrite. Use Annotated[dict, operator.or_] for merge behavior
  • Ollama response format — Even with "respond in JSON only" in the prompt, Ollama sometimes adds markdown backticks or preamble. Strip them before parsing
  • Start simple — Your first graph should be 3 nodes. Resist adding agents/A2A here. Get the skeleton working, then layer on complexity
  • Debugging tip — Add print(state.keys()) at the start of each node while developing. Remove later

Why RAG Matters Here

Without RAG, your agents review code using only the LLM's training data — generic knowledge about good code. WITH RAG, agents have access to specific standards (OWASP rules, your team's coding conventions, PEP 8). It's the difference between "this looks bad" and "this violates Rule 4.2 of your team's style guide." RAG is also the #1 most-asked-about pattern in AI interviews.

→
How — Step by Step
  • Gather knowledge docs — Download OWASP Top 10 as markdown, copy PEP 8 key rules, write sample team conventions. Drop into /knowledge/security/, /knowledge/quality/, etc.
  • Build the chunker — Split documents into chunks of ~500 tokens with ~50 token overlap. For code docs, split at section headers, not mid-paragraph. Use LangChain's RecursiveCharacterTextSplitter
  • Embed chunks — Use sentence-transformers/all-MiniLM-L6-v2 (runs locally, no API key). Each chunk becomes a 384-dim vector
  • Store in ChromaDB — Create 4 collections. Each chunk stored with metadata: { source_file, section, category }
  • Build retriever function — retrieve(query: str, collection: str, top_k: int = 5) → List[Document]. Returns chunks sorted by similarity score
  • Build ingestion CLI — python -m codesentinel.rag.ingest processes all files in /knowledge/ and loads them
◆
Concepts You'll Learn
  • Embeddings — Convert text into numbers (vectors) that capture meaning. Similar text = similar vectors. "SQL injection" and "unsanitized input" have close vectors even though the words differ
  • Vector database — ChromaDB stores vectors and finds the most similar ones fast. Think of it as "semantic search" — find documents by meaning, not keywords
  • Chunking strategy — Too small = lost context. Too large = noisy retrieval. 500 tokens with overlap is a good starting point for technical docs
  • Collections — Separate collections per domain so the Security Agent only searches security knowledge, not architecture docs. Reduces noise, improves relevance
  • Why local embeddings? — MiniLM-L6-v2 runs in ~50ms per chunk on CPU. No API key, no cost, no network dependency. Production systems might use OpenAI embeddings, but local is perfect for learning
!
Gotchas & Tips
  • ChromaDB persistence — By default it's in-memory and gone on restart. Use PersistentClient(path="./chroma_data") to save to disk
  • Chunk overlap — Without overlap, a sentence split across two chunks loses meaning in both. 50-token overlap ensures continuity
  • Ingestion is slow, retrieval is fast — Ingest once (minutes), query thousands of times (milliseconds). Don't re-ingest on every run
  • Test retrieval quality — Ask "SQL injection prevention" and check if OWASP A03 comes back. If not, your chunking or embedding is wrong

Why Dedup Is Harder Than It Looks

4 agents reviewing the same code WILL produce overlapping findings. Quality Agent says "bad naming." Architecture Agent says "violates convention." They're pointing at the same line for related but different reasons. Without a resolver, the PR comment has 4 redundant entries. With a resolver, it has 1 merged finding with both perspectives. Why HITL Matters for Real AI Systems

AI systems make mistakes. When the model is unsure (confidence < 0.5), the responsible choice is to ask a human. This is the difference between a toy project and a production AI system. HITL also generates labeled data — when a developer confirms or rejects a finding, that's feedback you can use to improve prompts. How — Step by Step

  • Add interrupt to resolve node — In the conflict resolution node, filter findings where confidence < 0.5. Call interrupt({"pending_findings": low_confidence_findings}). Pipeline freezes here
  • Build pending endpoint — GET /api/review/{review_id}/pending returns the low-confidence findings that need human judgment
  • Build respond endpoint — POST /api/review/{review_id}/respond with body {"finding_id": "...", "action": "confirm|reject|skip"}. Updates the finding in state, then calls graph.invoke(None, config={"thread_id": review_id}) to resume
  • Implement timeout — Background task: if no response within 5 minutes, auto-skip all pending findings with a "status": "unverified" label. Pipeline resumes with the unverified label visible in the output
  • Log human feedback — Every confirm/reject is gold for eval. Store in SQLite: human_feedback(review_id, finding_id, action, timestamp)

  • Human-in-the-loop pattern — AI handles the 90% it's confident about. Humans handle the 10% that's ambiguous. This is how production AI systems scale without sacrificing quality
  • Active learning — Human feedback on uncertain cases is the most efficient training signal. You're not labeling random data — you're labeling exactly the cases the model struggles with

Why Agents Need to Fetch Context

Agents only see the diff — changed lines plus ~3 lines of context. When an agent sees from utils.auth import verify_token in the diff, it doesn't know what verify_token does, what exceptions it throws, or how it's supposed to be called. Without this, the agent can only say generic things like "handle errors." With tool-use, it fetches the auth module summary, sees that verify_token raises TokenExpiredException, and produces: "Line 42: missing try/except for TokenExpiredException — this will return 500 instead of 401." That's the quality gap between a toy and a useful tool.

→
How — Step by Step
  • Define 3 tool functions — fetch_file_summary(path) → str (summarized by a quick LLM call), fetch_function(path, function_name) → str (AST-parsed extraction), fetch_file(path) → str (raw content, capped at 2000 tokens)
  • Build the summarizer — A lightweight LLM call: "Summarize this file in 200 tokens: what it does, key exports, patterns used, exceptions thrown." Uses the same Ollama model but with a short prompt
  • Build function extractor — Use Python's ast module to parse the file and extract a specific function by name. Returns the function source with docstring. No LLM needed — pure code
  • Register tools with LangGraph — Use LangGraph's ToolNode pattern. Each agent node becomes a tool-calling node: generate → detect tool call → execute tool → feed result → generate final review
  • Update agent prompts — Add a "Available Tools" section explaining when to use each tool. "If you see an import you don't recognize, call fetch_file_summary. If you need exact implementation, call fetch_function."
  • Cap tool calls — Max 3 tool calls per agent per review. After 3, the agent must proceed with whatever context it has. Prevents runaway token usage
  • Fetch files via GitHub API — repo.get_contents(path, ref=pr.head.sha) returns the file at the PR's branch. Decode from base64

Concepts You'll Learn
  • LangGraph ToolNode — The pattern for giving graph nodes access to tools. The node generates a response, if it contains a tool call the ToolNode executes it, feeds the result back, and the node continues. Same pattern Claude uses for web search
  • Two-pass summarize-then-fetch — Summary first (cheap, ~200 tokens), specific code only if needed (targeted, ~100-500 tokens). Saves context window budget compared to always fetching full files
  • AST-based code extraction — Python's ast module parses source code into a tree. You can find any function/class by name and extract just its source. No regex, no string matching — proper parsing

  • Summarizer adds latency — Each summary is an extra LLM call (~5s on Ollama). If agents request 3 summaries each, that's 60s of extra latency across 4 agents. Consider caching summaries per review

  • Gather real PRs — Find 5-10 open-source PRs of varying complexity. Good sources: popular Python repos (FastAPI, httpx, Pydantic), your own past PRs at work (anonymized)
  • Run baseline — Review all PRs with current prompts. For each, note: correct findings, false positives, missed issues, unhelpful suggestions
  • Categorize failures — Group by type: "hallucinates line numbers" → fix line number formatting in prompt. "Flags style issues as critical" → add severity calibration examples. "Misses security issue" → improve RAG query construction
  • Iterate per agent — Change one thing at a time. Re-run. Compare. Record the delta. One prompt change might fix 3 false positives but introduce 1 new one
  • Version prompts — PROMPTS.md logs every change: "v2.1: Added 'do not flag renamed variables as naming issues' — reduced false positives from 30% to 18%"
  • Final pass — Run all 10 PRs with the final prompts. Record: overall false positive rate, recall, subjective quality score (1-5 per review)
◆
Concepts You'll Learn
  • Systematic prompt optimization — Not "try random changes and hope." Define a metric, change one variable, measure the impact. This is the scientific method applied to prompts
  • Prompt versioning — Every production AI system versions its prompts like code. You need to know which prompt version produced which results. PROMPTS.md is your changelog
  • Few-shot calibration — Adding 2-3 examples of correct severity classification to the prompt is often more effective than paragraphs of instructions. "Here's a critical finding" + "here's an info finding" = instant calibration
  • Negative examples — "Do NOT flag renamed variables" or "Do NOT report style preferences for languages you're not sure about." Explicit negatives reduce specific false positive categories
!
Gotchas & Tips
  • Don't overfit to your test set — If you tune prompts until they're perfect on 10 PRs, they might be terrible on PR #11. Keep 2 PRs as a "holdout" — don't tune on them, just validate
  • Temperature matters here — Try 0.0, 0.1, 0.2 across your test set. Lower isn't always better — sometimes 0.1 catches issues that 0.0 misses because of slight exploration
  • Context window pressure — Large PRs push against the context limit. If reviews get worse on big PRs, your prompt + RAG + diff exceeds the model's effective attention. Chunk large diffs per-file

Why a Golden Test Set

You can't measure what you can't define. The golden test set is your ground truth — PRs with known issues and labeled expected findings. Without it, "82% recall" is meaningless because there's no definition of "correct." This is the same concept as labeled datasets in ML: you need ground truth to compute precision, recall, and F1. It's also the #1 thing that separates "I built a demo" from "I built a system with measurable quality."

Why Build an Eval Scorer

This story turns "it seems to work" into "82% recall, 75% precision, F1 = 0.78." Numbers you can put on your README, in your resume, and say in interviews. The scorer also measures the VALUE of your architecture decisions: "RAG improved recall by 15%" and "A2A reduced false positives by 10%." These deltas prove that your architecture wasn't over-engineered — each component measurably contributed.

→
How — Step by Step
  • Run pipeline against golden set — python -m codesentinel.eval iterates over all 10 test PRs, runs the full pipeline, collects outputs
  • Match findings to labels — For each finding, check if a label exists at the same file + overlapping line range + matching category. Matched = true positive. Unmatched finding = false positive. Unmatched label = false negative
  • Compute metrics per agent — Precision = TP / (TP + FP). Recall = TP / (TP + FN). F1 = 2 * (P * R) / (P + R). Compute for each agent separately AND overall
  • Ablation runs — Run 3 configurations: (1) baseline — no RAG, no A2A, (2) RAG only — RAG enabled, A2A disabled, (3) full system — both enabled. Compare metrics across all three
  • Generate report — Output as JSON (machine-readable) and markdown (human-readable). The markdown becomes the eval section of your README
  • Compute deltas — "RAG lift" = full_recall - baseline_recall. "A2A lift" = full_precision - rag_only_precision. These are the numbers that prove architectural value
◆
Concepts You'll Learn
  • Precision vs recall — Precision: "of everything I flagged, how much was real?" Recall: "of everything real, how much did I catch?" They trade off — you can get 100% recall by flagging everything, but precision drops to 5%
  • F1 score — The harmonic mean of precision and recall. Balances both. F1 = 0.78 means your system is reasonably good at both catching issues AND avoiding false positives
  • Ablation study — Removing one component at a time to measure its contribution. Standard ML research technique. "Without RAG, recall drops 15%" proves RAG is valuable
  • Fuzzy matching — Labels say "line 42" but the finding says "lines 40-44." You need overlapping range matching, not exact equality. Same for categories: "sql_injection" matches "injection"
!
Gotchas & Tips
  • LLM non-determinism — Run the eval 3 times and average. Even at temperature=0, Ollama can produce slightly different outputs. Report mean ± std
  • Don't game the metrics — You can inflate recall by flagging everything. Real value is a balanced F1. Aim for recall > 80% AND precision > 70%
  • Ablation takes time — 3 configurations × 10 PRs × 60s each = 30 minutes per eval run. Automate it and go for a walk

Why This Is the Final Boss

This story ties everything together. The eval results table in the README is the project's proof of value — hard numbers that anyone can verify by running the eval themselves. Adding eval to CI means quality can never silently regress — if you change a prompt and recall drops below 75%, the build fails. This is the gold standard for production AI: automated quality gates. It's also the story that completes your "I built a full AI engineering lifecycle" narrative.

→
How — Step by Step
  • Build the README table — Markdown table: | Agent | Precision | Recall | F1 | RAG Lift | A2A Lift |. Populate with CS-026 results. Add an overall row
  • Add eval to CI — New GitHub Actions job: eval. Uses a lightweight model (or mocked LLM for speed). Runs python -m codesentinel.eval --ci. The --ci flag uses fixtures instead of live LLM calls, or runs against a smaller golden subset
  • Set quality gate — if overall_recall < 0.75: sys.exit(1). CI fails, PR can't merge. Choose the threshold based on your current metrics minus a small buffer
  • Track historical results — Store eval results in eval/results/ directory with timestamps: eval_2025-06-15.json. A simple diff shows what changed between prompt versions
  • Optional: visual dashboard — A simple HTML page (or even a GitHub Pages deployment) that charts eval metrics over time. Overkill for MVP but impressive for demos
◆
Concepts You'll Learn
  • Quality gates in CI — The same concept as "tests must pass to merge" but applied to AI quality. If recall drops, you investigate before shipping. This prevents "we changed a prompt and didn't realize it broke security detection"
  • Regression detection — With historical eval results, you can catch slow quality decay. Recall was 85% last month, now it's 78%. Something changed. The eval history tells you when
  • Eval-driven development — The AI equivalent of test-driven development. Define the expected quality, build until you meet it, add a gate to maintain it. The eval framework is the safety net that lets you iterate on prompts with confidence
!
Gotchas & Tips
  • CI eval must be fast — Full eval (10 PRs × live LLM) takes 30+ minutes. CI should use a subset (3 PRs) or mocked LLM responses that test the scoring logic, not the model quality. Save full eval for manual runs
  • Don't set the gate too tight — If your current recall is 82%, set the gate at 75%, not 80%. LLM output has natural variance. A gate at 80% will flake and you'll disable it out of frustration
  • Version the golden set too — If you add new test PRs, old eval results aren't comparable. Track the golden set version alongside eval results
  • This story is your mic drop — When an interviewer asks "how do you know it works?", you say "automated eval framework with precision/recall metrics, ablation studies, and CI quality gates." That's a senior engineer answer
